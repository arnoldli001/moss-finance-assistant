## 一、FastAPI 应用初始化陷阱

### 问题现象
`server.py` 中 `app = FastAPI()` 被实例化了**两次**，第二次覆盖了第一次，导致 CORS 中间件丢失，前端跨域请求全部失败。

### 根因分析
```python
app = FastAPI(title="DeepAgents API")        # 第一次：注册了 CORS
app.add_middleware(CORSMiddleware, ...)

app = FastAPI(title="DeepAgents API", lifespan=lifespan)  # 第二次：覆盖了第一个 app
```
Python 执行顺序是从上到下，第二个 `app` 覆盖了第一个，但 CORS 中间件是注册在第一个 `app` 上的，所以中间件丢失。

### 修复方案
合并为一次实例化，CORS 在 app 创建之后注册：
```python
app = FastAPI(title="DeepAgents API", lifespan=lifespan)
app.add_middleware(CORSMiddleware, ...)
```

### 经验教训
- FastAPI 中间件必须在 `app` 实例化之后注册，且 `app` 只能创建一次
- 代码重构时注意检查是否有重复定义

## 二、WebSocket 断连导致页面卡死

### 问题现象
前端发送第一条消息后正常，但发送第二条消息时**页面无响应**，输入框卡住无法操作。

### 根因分析
三层问题叠加：

1. **前端 WebSocket 无心跳机制**：长时间空闲导致连接被关闭
2. **前端无自动重连**：`ws.onclose` 只打印日志，不重连
3. **`isRunning` 状态锁未释放**：`task_result` 消息因 WebSocket 断开未到达，`setRunning(false)` 永远不被调用，第二次发送被 `if (isRunning) { alert('当前任务进行中'); return; }` 拦截

### 修复方案
```javascript
// 1. 心跳：每 30 秒发送 ping
function startHeartbeat() {
  wsHeartbeatTimer = setInterval(() => {
    if (ws && ws.readyState === WebSocket.OPEN) ws.send('ping');
  }, 30000);
}

// 2. 自动重连：断开后重试 3 次
ws.onclose = () => {
  if (isRunning) {
    appendMessage('error', '⚠️ 连接断开，任务状态可能丢失');
    setRunning(false);  // 解锁
  }
  if (wsReconnectCount < 3 && currentSessionId) {
    wsReconnectCount++;
    setTimeout(() => connectWS(currentSessionId), 2000 * wsReconnectCount);
  }
};

// 3. 超时保护：5 分钟自动解锁
runningTimeoutTimer = setTimeout(() => {
  if (isRunning) setRunning(false);
}, 300000);
```

### 经验教训
- WebSocket 长连接**必须有心跳**，否则会被中间网络设备关闭
- 状态锁（`isRunning`）必须有**超时兜底**，不能依赖单一事件释放
- 断连时必须**清理状态**，避免死锁

## 三、WebSocketDisconnect 异常逃逸

### 问题现象
两个浏览器窗口打开同一会话，server 抛出 `WebSocketDisconnect: (<CloseCode.NO_STATUS_RCVD: 1005>, '')`，异常未被 try/except 捕获。

### 根因分析
两个问题叠加：

1. **`manager.connect` 在 try 块之外**：
```python
await manager.connect(websocket, thread_id)  # ← 在 try 外！
try:
    while True:
        data = await websocket.receive_text()
except WebSocketDisconnect:
    ...
```

2. **同 thread_id 连接覆盖**：`active_connections[thread_id] = websocket` 直接覆盖旧连接，旧连接变孤儿。`disconnect` 按 thread_id 删除，会误删新连接。

### 修复方案
```python
# 1. connect 移入 try 块，用 finally 清理
try:
    await manager.connect(websocket, thread_id)
    while True:
        data = await websocket.receive_text()
except WebSocketDisconnect:
    pass  # 正常断开
finally:
    manager.disconnect(websocket, thread_id)

# 2. connect 时先关闭旧连接
async def connect(self, websocket, thread_id):
    if thread_id in self.active_connections:
        old_ws = self.active_connections[thread_id]
        await old_ws.close()  # 关闭旧连接
    await websocket.accept()
    self.active_connections[thread_id] = websocket

# 3. disconnect 按对象匹配，避免误删
def disconnect(self, websocket, thread_id):
    if self.active_connections.get(thread_id) is websocket:  # ← 对象比对
        del self.active_connections[thread_id]
```

### 经验教训
- WebSocket 异常处理必须覆盖**所有代码路径**，包括 `accept` 阶段
- 同一 key 的连接管理要处理**新旧覆盖**问题
- 资源清理用 `finally` 确保执行，用**对象比对**避免误删

## 四、pyright 类型检查标红（20 处）

### 问题现象
项目中 6 个文件共 20 处 pyright 类型错误，IDE 大面积标红。

### 典型问题分类

| 类型 | 示例 | 修复方式 |
|------|------|----------|
| `Optional` 未判空 | `file.filename`（`str \| None`）直接用于 `Path /` | 添加 `if not file.filename: continue` |
| 库类型存根不匹配 | `sys.stdout.reconfigure`（`TextIO` 无此方法） | `# type: ignore[attr-defined]` |
| `yaml.safe_load` 返回 `Optional` | `prompt_yaml_content["main_agent"]` 下标 None | `isinstance` 判空 + 返回类型注解 |
| `@tool` 装饰器返回 `BaseTool` | `execute_sql_query(...)` 不可直接调用 | 改用 `.invoke()` |
| 库 API 签名不匹配 | `create_deep_agent(model=...)` 类型不兼容 | `# type: ignore[arg-type]` |

### 经验教训
- `Optional[T]` 类型的变量**必须判空**后才能使用
- 第三方库的类型存根可能不完整，用 `# type: ignore[具体规则]` 抑制（避免笼统的 `# type: ignore`）
- `@tool` 装饰器返回的是 `BaseTool` 实例，不是原函数，调用方式不同

## 五、ngrok 隧道 "already online" 错误

### 问题现象
重启 server 时 ngrok 报 `ERR_NGROK_334: The endpoint is already online`，隧道创建失败。

### 根因分析
ngrok 免费版分配**固定域名**，每次启动用同一域名。上次 server 被 `StopCommand` 强制终止，ngrok 进程未正常关闭，云端隧道仍标记为 online。`pyngrok.kill()` 只杀本地进程，云端状态需 60 秒超时才释放。

### 修复方案
用 `subprocess` 直接调用 ngrok 命令行，加 `--pooling-enabled` 参数：
```python
ngrok_bin = get_ngrok_config().ngrok_path
ngrok_proc = subprocess.Popen(
    [ngrok_bin, "http", "8000", "--pooling-enabled", "--log=stdout"],
    stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL
)
# 通过本地 API 获取公网 URL
resp = urllib.request.urlopen("http://127.0.0.1:4040/api/tunnels")
public_url = json.loads(resp.read())["tunnels"][0]["public_url"]
```

### 经验教训
- ngrok 免费版域名固定，进程异常终止后云端隧道不会立即释放
- `--pooling-enabled` 允许多实例共享同一域名，彻底避免冲突
- `pyngrok` 的 `connect()` 不支持 `--pooling-enabled`，需用 `subprocess` 直接调命令行

## 六、AsyncSqliteSaver 初始化时机

### 问题现象
`RuntimeError: no running event loop` — 同步版 `SqliteSaver` 不支持 `astream` 异步方法。

### 根因分析
`SqliteSaver`（同步）在 async 上下文中调用 `aget_state_history` 等 async 方法会报错。`AsyncSqliteSaver` 需要 `aiosqlite` 连接，必须在事件循环内初始化。

### 修复方案
改为**惰性初始化**，在首次 `await get_main_agent()` 时建立连接：
```python
async def get_main_agent():
    global _main_agent, _checkpointer
    if _main_agent is None:
        conn = aiosqlite.connect(str(_checkpointer_db))
        await conn.__aenter__()  # 必须在事件循环内
        _checkpointer = AsyncSqliteSaver(conn)
        await _checkpointer.setup()
        _main_agent = create_deep_agent(..., checkpointer=_checkpointer)
    return _main_agent
```

### 经验教训
- 异步 SQLite saver 必须在事件循环内初始化，不能在模块加载时
- 用**惰性初始化模式**延迟到首次使用时创建，确保事件循环已运行

## 七、Tavily API ConnectionResetError 10054

### 问题现象
连续发送两个请求（间隔 20 秒），第二个请求报 `ConnectionResetError: [WinError 10054]`。

### 根因分析
Tavily API 服务器关闭了 HTTP keep-alive 连接，客户端复用了已关闭的连接。

### 修复方案
添加**指数退避重试**（3 次，2s/4s/8s 间隔）：
```python
for attempt in range(3):
    try:
        response = requests.post(...)
        return response.json()
    except (ConnectionResetError, ConnectionAbortedError, BrokenPipeError):
        if attempt < 2:
            time.sleep(2 ** (attempt + 1))
            continue
        raise
```

### 经验教训
- HTTP keep-alive 连接可能被服务端随时关闭，客户端必须处理连接重置
- 指数退避重试是网络请求的标配，避免瞬时故障导致整个任务失败

## 八、IMA 知识库 API 端点错误

### 问题现象
调用 `search_knowledge_base` 端点返回空结果，但知识库中确实有数据。

### 根因分析
RAGFlow SDK 的 `search_knowledge_base` 方法与 IMA API 不兼容，返回空结果。需要用 IMA 的 `search_knowledge` 端点。

### 三步调用链
```
search_knowledge → get_media_info → get_doc_content
（搜索）           （获取媒体信息）   （获取文档内容）
```

### 经验教训
- 第三方 SDK 的方法可能与实际 API 不匹配，需要直接调 HTTP API
- IMA API 只返回标题和元数据，获取完整内容需要三步调用链
- 短关键词（如"国产替代"）比长查询返回更多结果
