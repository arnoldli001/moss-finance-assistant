# 分级降级策略（Degradation Tiers）

本文档定义金融系统从“全量风控”到“紧急裸奔”的四个降级层级。**在系统故障时，禁止直接跳到 Tier 4，必须逐级降级。**

## 降级层级定义

| 层级 | 名称 | 验证范围 | 风险敞口 | 触发条件 |
| :--- | :--- | :--- | :--- | :--- |
| **Tier 1** | **全量验证（Normal）** | 盘前风控 + 实时持仓 + 对手方信用 + 监管约束 | **零风险** | 默认状态 |
| **Tier 2** | **缓存验证（Stale Cache）** | 回退到 5 秒前的持仓/资金快照 | **有限风险**（已知） | 实时数据库查询延迟 > 100ms |
| **Tier 3** | **名义限额（Notional Cap）** | 仅检查单笔订单的名义金额上限（如 < 100万） | **可接受的最大风险敞口** | 缓存快照不可用或过期超过 1 分钟 |
| **Tier 4** | **人工覆写（Override）** | 零自动校验，完全依赖交易员手工判断 | **不可控风险（需事后审计）** | 自动决策系统完全不可用，且人工授权通过 |

## 各层级日志要求

- **Tier 1**：正常 INFO 级别日志。
- **Tier 2**：**WARN** 级别日志，必须标注 `degraded_reason="CACHE_HIT"`。
- **Tier 3**：**ERROR** 级别日志，触发 P1 告警，必须在订单备注中标记 `RISK_LEVEL=TIER_3`。
- **Tier 4**：**CRITICAL** 级别日志，触发 P0 告警，必须记录授权人的 `user_id` 和授权时间戳。

## 降级恢复（Upscale）

系统必须每 **30 秒** 探测一次上游依赖（如数据库、风控服务）是否恢复。一旦依赖恢复连续健康 3 次，系统应**自动升级**（Upscale）回 Tier 1，无需人工干预。
